# NetWasm 0.10.2: faster array and loop code

NetWasm 0.10.2 is available on NuGet.org.

This release makes code that works on arrays inside loops faster. On our
quicksort benchmark NetWasm took 33% more time than Mono AOT in 0.10.1; it now
takes 7% less. NetWasm now takes less time than Mono AOT, or matches it, on
every workload we publish, with or without allocation.

## Performance

- At `O3`, a small method called inside a loop is inlined when it is a straight
  run of up to 32 instructions that makes no calls and does not branch,
  allocate or throw, such as a tuple swap of two array elements.
- An inlined call reads an argument that is a plain local or parameter where
  the callee reads it, instead of copying it first. Array checks then see the
  caller's array rather than a copy, so they can use what is already known
  about it.
- An array access skips its null and bounds checks when an earlier access to
  the same array and index already made them, and its null check when an
  earlier access to the same array did. Methods with exception handlers keep
  every check.
- A loop inside another loop no longer reloads each array's length and data on
  entry, and a method reads an array parameter's length and data once when the
  parameter is never assigned.

Median time at `NetWasmOptimization=O3`, against the 0.10.1 figures from the
same host and harness:

| Workload | NetWasmGC 0.10.1 | NetWasmGC 0.10.2 | Compact 0.10.1 | Compact 0.10.2 | Mono AOT |
| --- | ---: | ---: | ---: | ---: | ---: |
| Quicksort | 77.2 ms | 54.0 ms | 77.4 ms | 53.9 ms | 58.0 ms |
| n-body | 53.5 ms | 52.9 ms | 53.3 ms | 53.0 ms | 53.3 ms |
| CRC-32 | 47.7 ms | 47.4 ms | 47.5 ms | 47.4 ms | 47.4 ms |
| Preallocated transaction | 18.6 ms | 18.8 ms | 18.8 ms | 19.1 ms | 23.5 ms |

The allocation workloads run within run-to-run variation of 0.10.1, and peak
linear memory is unchanged. The print-`42` component published at `Oz` with
Compact is unchanged at 43,109 bytes. See [Performance](../performance.md) for
the method and the desktop .NET figures.

## Fixes

This failure is present in 0.10.1.

- Turning on `NetWasmStructuredDiagnostics` after a build without it failed with
  NW1010, because the build reused the module compiled without diagnostics. The
  setting now triggers a recompile.

## Browser compilation

- `BrowserCompilationResult` returns the compilation's diagnostic artifacts:
  the exception type map, the module it belongs to and the manifest that binds
  them. A browser host can now name the type of an exception reported by a
  structured failure, as the SDK's hosts do.

## Validation

- The release workflow runs the complete compiler test suite, with each
  fixture's full matrix, and merges its code coverage, which must meet the
  coverage baseline before a release publishes. The README shows the latest
  release's coverage.
- New tests run programs on wasm32 and wasm64 that change a variable while
  passing it to an inlined call, or that make a skipped check fail, and compare
  each result with desktop .NET's.
- Every benchmark run's result matches the same program on desktop .NET 11.
