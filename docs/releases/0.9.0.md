# NetWasm 0.9.0: C# modules for web pages

NetWasm 0.9.0 is available on NuGet.org.

A `JsModule` project publishes C# `[JSExport]` methods as a typed JavaScript
module. A page imports it, calls the exports directly and closes it when done.
The same project can run in a Web Worker instead, or publish both. This
release also ships the time zones each application selects, reports the
caught cause of every execution failure, and fixes the issues reported against
0.8.1.

## JavaScript modules

- Added `<OutputType>JsModule</OutputType>`. Publish writes
  `browser/<AssemblyName>.mjs` and `.d.mts` declarations. `open()` starts an
  instance and returns one method per export, plus `close()` and `failure`.
  Each call to `open()` starts an independent instance.
- `NetWasmJavaScriptHosts` selects the host. With `page` (the default), exports
  run on the page's thread: synchronous exports return their values directly,
  `Task` exports return Promises, and import modules can use the DOM. With
  `worker`, the module runs in a Web Worker behind a Promise-based client.
  `page;worker` publishes both.
- Generated declarations name parameters after the C# parameters, or the WIT
  parameters for WIT workers (#92). Strings, arrays and `JSObject` are typed
  without `| null` when C# declares them non-nullable.
- Page exports can take and return `JSObject`. Number arrays marshal as the
  typed array with the same element type, in both directions. Async exports
  accept strings, number arrays and `JSObject`, and async imports can settle
  with them.
- On the page host, JavaScript that an import runs can call an export again
  before the import returns, nested up to 32 levels.
- `open()` options supply guest output, environment variables, import modules
  at runtime and a notification handler.
- Browser command deployments include a generated `run()` helper. It pins the
  deployment's build fingerprint and manifest digest, and uses the project's
  arguments, environment and grants.
- The publish directory is a static site. It needs no server code and no
  `Cross-Origin-Opener-Policy` or `Cross-Origin-Embedder-Policy` headers, and
  runs under `script-src 'self' blob: 'wasm-unsafe-eval'`.
- `dotnet new netwasm-app --host page` creates a module project and a page that
  opens it, calls an export and closes it. `--host worker` creates the worker
  form.

See [JavaScript interop](../javascript-interop.md) and
[C# Web Workers](../web-workers.md).

## Time zones

- `NetWasmTimeZone` items select the IANA zones an application ships, and
  `<NetWasmTimeZoneMode>Full</NetWasmTimeZoneMode>` ships every zone. Build,
  `dotnet run` and every publish write `<program>.wasm.tz-info` beside the
  primary Wasm from the IANA release pinned by NetWasm.Toolchain (2026c).
  Aliases ship with their zones.
- The data ships only when the application reaches a local-time API. Otherwise
  the build warns with NWSDK080. An unknown zone fails with NWSDK079.
- `TZ` stays an explicit setting, and NetWasm still defaults to UTC. A `TZ` that
  the deployment's data does not contain fails before managed code starts and
  names the zone. A page module can set `TZ` per instance with
  `open({ environment: { TZ } })`.

See [Time zone assets](../timezone-assets.md) for sizes and hosting.

## Failure detail

- An execution failure now carries `detail` whenever the host caught an error:
  that error's name and message on one line, at most 1,024 characters. For
  example, a deployment that reads the wall clock without a clock grant reports
  `detail: "TypeError: platform capability 'wallClock' was not granted"`. The
  local launcher replaces host paths in `detail` with `<host-path>`.

## Performance

- `NetWasmOptimization=O3` inlines small methods as .NET's JIT does, including
  members of generic types such as `ReadOnlySpan<T>` and `List<T>`, struct
  methods and constructors. O3 trades size for speed; `Os` and `Oz` keep their
  size-focused behavior.
- Comparisons of constant strings and UTF-8 literals fold at compile time at
  `O2`, `O3`, `Os` and `Oz`, and at `O3` also through small helper methods.
- A pattern such as `value is 1 or 3 or 5 or 7`, or a `switch` whose cases
  reach one or two outcomes, tests a bit mask instead of comparing each case,
  at `O1`, `O2`, `O3`, `Os` and `Oz`.
- At `O3`, a loop guarded by `i + c < array.Length` reads `array[i]` through
  `array[i + c]` without bounds checks, and so does `array[^1]` after a check
  that the array is not empty.
- In generic code, `value is int number` and similar tests no longer allocate
  when the type argument is a value type.
- A virtual or interface call on a local that holds a new object of one exact
  class calls that class's method directly, at `O1`, `O2`, `O3`, `Os` and `Oz`.
- An object that is created and never read, whose constructor only stores its
  arguments, is no longer allocated, at `O1`, `O2`, `O3`, `Os` and `Oz`.
- At `O3`, a struct with object or `ref` fields, such as `Span<T>` and
  `ReadOnlySpan<T>`, can live in WebAssembly locals instead of memory, and a
  struct is constructed directly in the local it is assigned to.
- At `O3`, a loop tests its condition before it starts and again at the end of
  each iteration. A loop whose condition first reads the `Length` of an array
  that the loop never reassigns checks that array for null once, before the
  loop.

## Fixes

- A delegate bound to a `[JSImport]` method group produced invalid WebAssembly
  (#89). Such delegates now call the import through a generated forwarder.
- Raw browser hosts rejected deployments whose runtime uses finalization or
  weak handles, and reported no cause (#89). Hosts now accept every runtime
  feature the compiler records.
- Every call from JavaScript into managed code registered the application's
  static roots again, with a search that grew quadratically (#89). Each
  instance now registers them once.
- Publishing a WIT worker on Windows failed with NW1009 (#90). CI now publishes
  a WIT worker on Windows.
- A method whose WebAssembly function body exceeds the 7,654,321-byte limit that
  browsers and Node enforce now fails the build with NW1013, which names the
  method (#93). The issue's reproduction with many reference locals now grows
  linearly.
- `Enum.GetName(Type, object)` and `Enum.IsDefined(Type, object)` compare an
  integer value with the enum's members as .NET does, including sign extension
  and values outside the underlying type's range.
- A method reference whose parent is a derived type now resolves to the method
  that a base type declares, including a constructed generic base.
- `Array.GetValue` on a nullable value-type array, such as `int?[]`, returned a
  non-null box for an element without a value. It now returns `null`.
- A top-level program that uses `await` now starts at its generated entry point,
  even when `partial class Program` declares another `Main`.

## Validation

- Page modules, worker modules, WIT workers, commands, time zone applications
  and the #89 reproductions pass in Chromium, Firefox and WebKit, in Debug and
  Release, built from the release candidate packages. Page modules and time
  zone applications run under the strict Content Security Policy above.
- A JavaScript callback into an application with 400 static roots costs the
  same as one with none: about 1 µs per call in Chromium.
- A synchronous page export call costs about 1.2 µs in Chromium and WebKit and
  about 6 µs in Firefox. A worker round trip costs 21 to 60 µs.
- The print-`42` component is byte-identical to 0.8.1 under every collector:
  47,798 bytes with the default Compact collector.
- Collector throughput and peak linear memory were measured again on 0.9.0;
  [Choosing a garbage collector](../runtime-garbage-collection.md#measured-performance)
  has the figures.
- Applications that use the released Libraries 0.8.0 packages pass on NetWasm
  0.9.0 with TUnit-NetWasm 0.9.0: JSON 49/49, Encoding 13/13 and Regex 28/28.

## Upgrading

- Unchecked conversions from `float` and `double` to `sbyte`, `byte`, `short`,
  `ushort` and `char` saturate at the destination's bounds, and NaN becomes 0,
  as in .NET 11. Earlier releases wrapped after converting to 32 bits, so
  `(byte)300.7` was 44 and is now 255.

- `JsWebWorker` is replaced by `JsModule`. Set
  `<OutputType>JsModule</OutputType>` and
  `<NetWasmJavaScriptHosts>worker</NetWasmJavaScriptHosts>` to keep a Web Worker.
  The old output type fails the build with a message that says so.
- The `NetWasmWorkerJavaScriptModule` item is renamed to
  `NetWasmJavaScriptModule`, because both hosts use it. The old name fails the
  build.
- `dotnet new netwasm-app --worker jsexport` is replaced by `--host worker`.
  `--worker` keeps `none` and `wit`.
- Republish `JsModule` deployments with 0.9.0. Generated hosts accept only the
  0.9.0 module contract.
- Generated declarations now use the C# parameter names and drop `| null` from
  non-nullable references, so TypeScript callers may see stricter types.
- Execution results can carry `detail`. Use TUnit-NetWasm 0.9.0 with NetWasm
  0.9.0, because TUnit-NetWasm 0.8.0 cannot read a failure that has it.
- A command application whose `Main` stays alive to answer JavaScript callbacks
  should become a `JsModule` and expose those callbacks as exports.
