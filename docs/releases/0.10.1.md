# NetWasm 0.10.1: faster code and an asynchronous Main

NetWasm 0.10.1 is available on NuGet.org.

This release makes compiled code faster and smaller. Methods no longer pay on
every call for exception handling they do not use, and CoreLib copies memory
and formats integers with far less work. On our allocation benchmarks
NetWasmGC now takes less time than desktop .NET 11's JIT on all three
workloads, and less than desktop NativeAOT on the retained object graph. The
print-`42` component is 10% smaller. Programs in the default command world can
now await, including from an asynchronous `Main`. Several loop shapes that
leave protected code no longer fail to compile or take the wrong path.

## Performance

- A method that can throw, through a null check, an array bound, checked
  arithmetic or an explicit `throw`, now calls a shared throw function instead
  of holding the throw itself. Wasmtime saves every callee-saved register on
  each call to a function that contains a throw, so these methods paid that
  cost even when nothing threw.
- Methods no longer wrap their bodies in a handler that only releases their
  frames when an exception passes through. The handler that catches the
  exception releases them instead. The wrapper had the same register cost.
- `Buffer.Memmove`, string copies and `Unsafe.CopyBlock` move up to 16 bytes
  with a few loads and stores, and longer blocks with `memory.copy`, instead of
  one element or byte at a time.
- Integer formatting reads its two-digit pairs directly from a constant string.
- Stack frames of up to 64 bytes are zeroed with stores instead of an
  out-of-line `memory.fill`.
- `Math.Pow` is about five times faster at `Oz` and twice as fast at `O3`.

Median time at `NetWasmOptimization=O3`, against the 0.10.0 figures from the
same host and harness:

| Workload | NetWasmGC 0.10.0 | NetWasmGC 0.10.1 | Compact 0.10.0 | Compact 0.10.1 |
| --- | ---: | ---: | ---: | ---: |
| Full transaction | 43.9 ms | 34.9 ms | 59.1 ms | 49.2 ms |
| Retained object graph | 8.8 ms | 4.6 ms | 17.8 ms | 12.5 ms |
| UI churn | 17.6 ms | 7.9 ms | 32.9 ms | 20.9 ms |

Peak linear memory is unchanged. NetWasmGC takes 41 to 73% less time than Mono
AOT and 8 to 53% less than desktop .NET 11's JIT. Desktop NativeAOT is still
faster on the full transaction and UI churn.

The print-`42` component published at `Oz` is 43,109 bytes with Compact
(47,895 in 0.10.0), 46,072 with NetWasmGC (50,855) and 39,078 with Bump
(43,864). See [Performance](../performance.md) and
[Choosing a garbage collector](../runtime-garbage-collection.md) for the
method, Mono AOT and desktop figures.

## Asynchronous programs in the command world

- An `await` that suspends no longer needs the reactor host. In 0.10.0 a
  program in the default command world failed with NW1009 even for
  `await Task.CompletedTask`.
- A world that imports `wasi:io/poll` and the monotonic clock runs its own event
  loop, modelled on Mono's `WasiEventLoop`. Ready work runs in order, and
  `Task.Delay` waits in `poll`.
- An asynchronous `Main` runs until its task completes, and a fault,
  cancellation or exit code surfaces as it would from a synchronous `Main`.
- A synchronous `Main` keeps Mono's behavior: work it defers never runs, and
  blocking on that work throws `PlatformNotSupportedException`. Unlike Mono,
  which spins, an asynchronous `Main` left waiting on work nothing can complete
  throws `InvalidOperationException`.
- The raw JavaScript host accepts typed arrays for numeric lists, as JavaScript
  Component Model providers return them. An asynchronous `Main` on wasm64
  needed this.

## Fixes

These failures are present in 0.10.0.

- A `while (true)` or `for (;;)` loop whose only exits leave a `lock`,
  `try`/`finally` or `try`/`catch` failed to compile.
- Optimized code for a loop body holding `lock` around a `foreach` followed by
  another statement failed to compile. `CookieContainer.Add` and `SetCookies`
  reach this shape.
- A loop whose `try` holds a nested `try`/`finally`, `try`/`catch` or `lock`
  followed by a `throw`, `return`, `break` or `goto` could run the code after
  that exit, for example the `catch` of a throw that never happened. This
  affected `do` loops, loops built with `goto` and asynchronous loops that
  resume inside the `try`.
- An asynchronous method whose loop holds a `try`/`catch` around an `await` and
  a nested `try`/`finally` returned without completing its task, and resuming
  it trapped. `ManagedWebSocket`'s close path has this shape.
- A delegate to a method the compiler expands inline, such as `Enum.HasFlag`,
  `Math.Abs`, `Math.Floor` or `Enum.ToString`, failed to compile with NW1008.
- A program that reaches `Array.GetValue` and uses a nullable enum elsewhere
  failed to compile with NW1008.
- `Math.Pow` could miss exact results such as `Math.Pow(3, 2)` by one unit in
  the last place. It now returns exact integral powers and matches the C
  library's result on every one of 1.2 million tested inputs.
- `await using (resource.ConfigureAwait(false))` failed to compile with CS0121.
- A call to a delegate's `BeginInvoke` or `EndInvoke` failed to compile with
  NW1003. Both now throw `PlatformNotSupportedException`, as on .NET.

## Validation

- The full compiler test suite passes with Compact, the default collector, in
  Debug and optimized builds on wasm32 and wasm64, against desktop .NET's
  results.
- Every benchmark run's result matches the same program on desktop .NET 11.

## Upgrading

- `ValueTaskExtensions` is removed. It had no .NET counterpart. Its
  `ValueTask` overloads were unreachable as extensions, because `ValueTask`
  declares `ConfigureAwait` itself, and its `IAsyncDisposable` overload made
  `await using` ambiguous. Call the instance `ConfigureAwait`, or
  `TaskAsyncEnumerableExtensions.ConfigureAwait` for an `IAsyncDisposable`.
